# 统一文档规范

## 1. 基本规则

- 文档使用 UTF-8 Markdown，一级标题仅出现一次。
- 命令注明运行目录和终端类型，仓库教程以 PowerShell 为主。
- 路径使用仓库相对路径，不写个人 Conda、IDE 或用户目录绝对路径。
- 环境变量只展示占位值，不展示真实密码、Token、API Key 或私钥。
- 已实现、部分实现、占位和规划功能必须明确区分。
- 链接使用相对路径，并在提交前验证目标文件存在。

## 2. 需求文档

需求编号统一使用：

```text
REQ-<模块>-<序号>
```

每条需求至少包含：

- 背景和用户价值；
- 输入、输出及权限；
- MVP 和优化优先级；
- 可验证验收标准；
- 依赖接口、数据源和风险。

需求变更必须同步开发计划、接口或数据约束，不能只修改页面说明。

## 3. API 文档

接口条目必须包含：

- HTTP 方法、路径、认证和权限；
- 请求参数或请求体；
- 成功响应和主要错误；
- 分页、状态枚举和幂等语义；
- PowerShell、curl 或前端调用示例；
- 当前实现状态。

API 变更必须同时更新后端 Schema、测试、OpenAPI、静态 API 参考、
前端类型和调用层。禁止静默改变公共字段。

## 4. 数据库变更

每个数据库 PR 必须包含：

- ORM 变更；
- 新 Alembic migration；
- upgrade 和 downgrade 行为；
- 数据迁移、兼容性和回滚风险；
- `upgrade → downgrade → upgrade` 验证结果。

不得修改已经进入共享主线的历史 migration 来伪装新变更。

## 5. Agent 文档

每个 Agent 能力至少记录：

- 用例名称和版本；
- Prompt 模板版本；
- 模型、温度、超时和结构化输出 Schema；
- RAG 数据来源、检索条件和引用格式；
- Memory 的范围、保存周期和隐私边界；
- 证据、置信度、规则校验和降级策略；
- 失败、超时、无证据和冲突证据处理；
- 离线评测集及核心指标。

生成内容不能直接提升为已验证事实。涉及图谱 L4/L5 时，必须保留来源 ID，
并遵守至少两个独立来源和 `0.75` 置信度门槛。

## 6. 开发计划

个人开发文档统一包含：

1. 职责与不负责事项；
2. 当前代码基线；
3. 上下游接口；
4. 4 周 MVP；
5. 后 8 周优化；
6. 交付物与验收；
7. 测试命令；
8. 分支和 PR 建议；
9. 协作风险。

## 7. 提交前检查

```powershell
git diff --check
git status --short
```

人工确认：

- 所有相对链接有效；
- 没有 `my-src`、长期 `develop` 等失效流程；
- 命令与当前目录结构一致；
- 示例没有真实密钥和个人绝对路径；
- 规划功能没有被写成已完成；
- API、迁移和测试数量没有脱离当前代码事实。

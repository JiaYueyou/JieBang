# 知识图谱未完成事项 — 六人分工与优先级

## Context

基于对 `data_analysis/scripts/` 和 `fyz-src/backend/` 的完整分析，知识图谱核心架构（Neo4j 五层森林、MySQL 事实库、Agent 抽取、图谱同步与查询 API）已基本搭建完成。但存在数据管道断裂、L4/L5 覆盖不足、性能索引缺失、验证流程不完整、前端联调缺口等问题。本项目不引入 Redis。

以下按六人职责范围分配剩余任务，每项标注优先级：**P0 = 先能跑**、**P1 = 有效果**、**P2 = 再优化**。

## 周欣雨：管理与决策端全栈

### A1. 替换占位路由为真实实现（P0）

当前 `changes`、`admin` 后端路由仍是占位实现（`make_placeholder_router`），前端对应页面无法获取真实数据。

**具体工作：**
- `changes` 路由：复用 `AnalysisService._capability_changes()` 的结果，提供 `GET /api/v1/jobs/{job_id}/changes?from_version=&to_version=` 和 `GET /api/v1/jobs/{job_id}/trend?months=6`，返回技能新增/修改/淘汰的结构化 diff
- `admin` 路由：实现 `GET /api/v1/admin/overview`（聚合 API 请求量、采集量、任务状态、服务健康）、`GET /api/v1/admin/health/services`（MySQL/Neo4j/DeepSeek 连通性检查）
- 新增 Service 层（`AdminService`）和对应 Schema，不直接在路由中写 SQL/Cypher
- 前端 Admin 页面接入真实接口，展示任务列表、数据源状态、同步快照

### A2. Dashboard 聚合端点（P1）

当前无 `GET /api/v1/dashboard/overview` 端点，前端工作台需要多次请求拼凑数据。

**具体工作：**
- 新建 `DashboardService`，聚合以下数据源到单次响应：
  - MySQL：在招岗位数、招聘看板各阶段人数、高匹配人才 Top 6
  - `AnalysisService`：热门岗位需求趋势（复用已有 `job_demand`）、新兴技能排行（复用已有 `emerging_skills`）
- 响应使用规格书中定义的 `DashboardOverview` DTO 结构
- 聚合结果不依赖 Redis，直接每次查询（短期可接受）

### A3. 岗位版本差异前端展示（P1）

后端已有 `job_version` 表和快照机制，但前端缺少版本对比视图。

**具体工作：**
- 实现 `GET /api/v1/jobs/{job_id}/versions` 前端页面（版本列表、时间线）
- 实现版本间技能差异对比（新增/移除/频率变化），调用 A1 中的 changes 接口
- 展示趋势图（技能频次随时间变化），调用已有 `AnalysisService` 数据

### A4. 企业技术栈 CRUD 完善（P1）

`InternalPosition` 模型用于转岗分析，但管理界面的独立增删改查不完整。

**具体工作：**
- 实现 `GET/POST/PUT/DELETE /api/v1/enterprise-tech` 完整 CRUD
- 支持从文件批量导入企业技术栈（复用 `career_service.py` 中的文件解析逻辑）
- 前端 Admin 页面增加企业技术栈管理 Tab

### A5. 图谱页面大数据量交互优化（P2）

**具体工作：**
- 前端 GraphView 增加虚拟滚动/分页加载（>1000 节点时）
- 截断提示和过滤建议（按 stack/level/node_type 引导用户缩小范围）
- L4/L5 候选审核前端界面（查看/批准/拒绝 GraphEnrichmentCandidate）

## 范彩艺：知识图谱与分级抽取

### E1. 技能词典统一（P0）

当前技能词典存在三处副本：`data_analysis/scripts/skill_dictionary.py`、`app/domain/skill_dictionary.py`、`app/services/skill_extractor.py`（内嵌规则），修改一处不同步另外两处。

**具体工作：**
- 确认 `app/domain/skill_dictionary.py` 为唯一权威来源
- 移除 `data_analysis/scripts/skill_dictionary.py` 的独立维护（改为 `from app.domain.skill_dictionary import ...`）
- `app/services/skill_extractor.py` 全部引用 `app/domain/skill_dictionary.py`，删除内嵌规则
- 成员 D 的爬虫标准化管线同步引用同一词典

### E2. Neo4j 索引补全（P0）

当前只有 `(namespace, id)` 唯一约束，缺少性能索引，搜索使用 `CONTAINS` 做全扫描。

**具体工作：**
- 添加全文搜索索引（规格书定义）：
  ```cypher
  CREATE FULLTEXT INDEX graph_name_search IF NOT EXISTS
  FOR (n:Job|SkillArea|TechStack|TechPoint|KnowledgePoint)
  ON EACH [n.name, n.description]
  ```
- 添加属性索引：`stack`、`level`、`frequency`、`importance`
- `Neo4jGraphRepository.ensure_schema()` 方法中统一创建
- `search` 接口改用全文索引查询（`CALL db.index.fulltext.queryNodes`）

### E3. 验证升级管线（P0）

当前 L1-L3 的 `JobSkillFact` 初始状态为 `unverified`，但图谱同步只使用 `verified` 状态的事实，缺少自动升级机制。

**具体工作：**
- 在 `graph_sync` 流程中增加验证步骤（`GraphService.sync()` 的 step 2.5）：
  - 对于每个 `JobSkillFact`（L1-L3），检查来源独立性和置信度
  - ≥2 个独立来源 且 平均置信度 ≥0.75 → 自动升级为 `verified`
  - 不满足条件的保留 `unverified`，等待更多数据源补证
- 验证结果记录到 `evidence_reference` 表

### E4. SAME_AS 跨岗位技能点去重（P1）

不同 TechStack 下的相同 TechPoint（如不同数据库的"索引优化"）当前各自独立，未合并。

**具体工作：**
- 在 `_append_verified_deep_nodes` 写入 L4 节点后，检测名称高度相似的 TechPoint（使用 `canonical_key` + 编辑距离）
- 相似度 ≥85% 的 TechPoint 对自动建立 `SAME_AS` 关系
- 低置信度（60-85%）的相似对标记为候选，等待人工审核
- 已建立 `SAME_AS` 的节点在 `expand` 和 `job_tree` 查询中自动展开关联节点

### E5. L4/L5 覆盖扩展（P1）

当前仅 Top-20 技能获得深层补全。

**具体工作：**
- 将 `_prepare_top_candidates` 的 `limit(20)` 改为配置参数（默认 50）
- 增加分批处理逻辑：每批 10 个技能，避免单次同步耗时过长
- 优先选择 `source_count ≥ 3` 且 `frequency` 最高的技能

### E6. 增量同步与定时调度（P1）

当前 `mode="incremental"` 路径基本是空壳，Celery Beat 未配置。

**具体工作：**
- 实现真正的增量同步：比较 `JobSkillFact.updated_at` 与上次同步时间，只处理变更的技能和岗位
- 增量模式下不重建已有节点，仅更新属性和新增节点
- 配置 Celery Beat 定时任务：
  ```python
  # 每日 06:00 增量采集后的自动图谱同步
  # 每周一 07:00 创建周快照 + L4/L5 补全
  ```
- 任务失败时记录错误并发送管理事件（不阻塞后续调度）

### E7. RELATED_TO 和 PREREQUISITE 关系写入（P2）

Agent 已支持输出这些关系，但 `_append_verified_deep_nodes` 未写入 Neo4j。

**具体工作：**
- 在 `GraphEnrichmentOutput` Schema 中增加 `related_skills` 和 `prerequisites` 字段（如未包含则协调成员 C 补充）
- `_append_verified_deep_nodes` 写入 `RELATED_TO`（TechStack-TechStack）和 `PREREQUISITE`（KnowledgePoint-KnowledgePoint）关系到 Neo4j
- 幻觉防控同样适用：这些关系也需 ≥2 来源验证

# 多源异构数据驱动岗位和能力图谱构建与动态演化分析研究

## 项目开发要求与目标（策划书）

---

## 一、项目概述

### 1.1 基本信息

| 项目 | 详情 |
| --- | --- |
| **项目名称** | 多源异构数据驱动岗位和能力图谱构建与动态演化分析研究 |
| **简称** | IT 岗位人才洞察与决策辅助平台 |
| **比赛类型** | 企业命题赛（科大讯飞发榜，自主命题） |
| **交付物** | 完整 Web 系统 + 现场演示 + 设计文档 + PPT + 演示视频 |
| **时间周期** | 12 周（约 3 个月） |
| **提交时间** | 暂定 9 月上旬 |
| **目标行业** | IT / 互联网（新一代信息技术领域：人工智能、大数据、智能系统、物联网等） |

### 1.2 赛题本质

构建一个**数据驱动的智能决策系统**——以岗位和能力为核心实体，以知识图谱为知识载体，以大模型为推理引擎，实现人岗匹配和趋势预测的闭环。

**核心逻辑链**：

> 新岗位发现 → 已有岗位能力动态更新 → 能力图谱全景可视化 → 人岗匹配度诊断 → 改进建议与学习路径推荐

### 1.3 项目定位

面向竞赛评委和行业应用场景，解决三大核心问题：

1. **新兴岗位发现与定义** — 如何从海量多源数据中精准发现并定义新兴岗位，更新既有岗位的能力要求，构建可动态更新的岗位能力图谱
2. **数据质量与幻觉防控** — 如何解决招聘数据中的"时滞"、"噪声"与"抄袭"问题，并通过技术手段有效防控 AI 生成内容"幻觉"的产生
3. **精准匹配与差距分析** — 如何实现高精度的简历解析与细粒度的人岗差距分析

### 1.4 目标行业聚焦

选择 **IT / 互联网** 行业深入做，比泛泛覆盖多行业效果更好。岗位选择范围包括人工智能、大数据、智能系统、物联网等领域。

## 二、四大核心功能模块

### 2.1 模块一：新岗位发现与定义

**需求描述**：识别市场上正在萌芽但尚未被标准化或逐渐兴起的新岗位，自动生成岗位定义，支持人工优化与动态更新。

| 需求编号 | 需求描述 | 优先级 |
| --- | --- | --- |
| REQ-1.1 | 从多源数据（招聘平台、行业报告、政策文件、学术论文）中发现新兴技能组合 | P0 |
| REQ-1.2 | 基于技能聚类和增长趋势，自动识别潜在新岗位 | P0 |
| REQ-1.3 | 生成岗位定义：岗位名称、核心职责、必备技能、加分技能、典型行业应用场景 | P0 |
| REQ-1.4 | 支持人工审核和优化自动生成的岗位定义 | P0 |
| REQ-1.5 | 支持增量更新，定期爬取触发新岗位检测 | P1 |

**示例**：Prompt Engineering（提示工程）→ Context Engineering（上下文工程）→ Harness Engineering（驾驭工程）

### 2.2 模块二：既有岗位能力动态更新

**需求描述**：针对现有岗位（如 Java 开发工程师），识别其能力要求随时间的变化趋势。

| 需求编号 | 需求描述 | 优先级 |
| --- | --- | --- |
| REQ-2.1 | 对比不同时间段同一岗位的技能要求差异 | P0 |
| REQ-2.2 | 明确标注新增、删除、修改的能力项 | P0 |
| REQ-2.3 | 提供更新说明及数据源引用 | P0 |
| REQ-2.4 | 支持版本化管理和时间维度查询 | P1 |
| REQ-2.5 | 示例：Java 工程师不仅需懂 Java，还需会 RAG、AI 能力、全栈技能等 | P1 |

### 2.3 模块三：全景图谱可视化

**需求描述**：展示领域内岗位的能力要求，颗粒度到"技能点"级别，支持交互探索。

| 需求编号 | 需求描述 | 优先级 |
| --- | --- | --- |
| REQ-3.1 | 岗位-技能关联网络可视化（力导向图） | P0 |
| REQ-3.2 | 按技术栈切换视图（AI / 大数据 / 物联网 / 后端 / 前端等） | P0 |
| REQ-3.3 | 按级别切换视图（初级 / 中级 / 高级） | P0 |
| REQ-3.4 | 支持节点展开/收起/搜索/过滤 | P0 |
| REQ-3.5 | 支持版本化管理和时间维度查询（"某技能在过去 N 个月的需求变化"） | P1 |
| REQ-3.6 | 支持时序图谱快照对比 | P1 |

**验收标准**：
- 图谱可视化页面能正常加载并交互（1000 节点内不卡顿）
- 图谱查询（3 层关系）响应时间 ≤ 2 秒

### 2.4 模块四：人岗匹配度诊断

**需求描述**：支持解析简历（PDF/Word），进行多维度匹配分析和差距诊断。

| 需求编号 | 需求描述 | 优先级 |
| --- | --- | --- |
| REQ-4.1 | 简历解析：支持 PDF/Word 格式，提取技能、工作经历等字段 | P0 |
| REQ-4.2 | 简历提取准确率 ≥ 90% | P0 |
| REQ-4.3 | 多维度匹配分析：语义相似度 + 图谱路径距离 + 技能覆盖率 | P0 |
| REQ-4.4 | 输出匹配度评分和详细技能差距清单 | P0 |
| REQ-4.5 | 提供改进建议与学习路径规划 | P1 |
| REQ-4.6 | 能力差距可视化：将求职者能力与目标岗位的差距以图谱路径形式直观展示 | P1 |

**验收标准**：
- JD 解析准确率 ≥ 90%

- 匹配准确率 ≥ 90%
- 匹配分析（10 个目标岗位）计算时间 ≤ 5 秒

## 三、创新性要求

### 3.1 多源异构数据清洗与交叉验证融合机制

- **核心目标**：解决数据的"时滞"与"噪音"问题
- **技术方案**：
  - 至少覆盖 **3 类以上数据源**（招聘平台、企业官网、行业报告、政策文件、学术论文等）
  - 建立 ETL 管道，统一 Schema
  - 为每条数据标注时间戳和来源
  - 设计数据质量评分体系
  - 利用大模型进行实体对齐和去重
  - 岗位名称对齐、技能标签归一化（如"Java 开发"与"Java 工程师"）

### 3.2 能力"幻觉"防控

- **核心目标**：基于数据交叉验证的图谱事实校验，有效防控 AI 生成内容的"幻觉"
- **技术方案**：
  - 设计基于图谱事实的校验机制：所有 AI 生成的能力描述必须可回查 Neo4j 图谱节点进行验证
  - 每条能力更新记录来源 URL、抽取时间、置信度分数、验证状态
  - 跨源验证：每个能力声明至少需 2 个独立数据源支持
  - 图谱 + RAG 融合推理：将图谱结构化知识注入 RAG 流程，实现"图谱引导的检索增强生成"
  - 准备 20+ 幻觉测试用例，验证检测率

### 3.3 其他创新建议

- **动态演化预测**：不仅展示历史变化，还预测未来趋势（如"未来 6 个月哪些技能需求将上升"）
- **能力差距可视化**：将求职者能力与目标岗位要求的差距以图谱路径形式直观展示

## 五、技术架构

### 5.1 五层架构设计

依照比赛官方推荐，系统采用五层架构：

```
┌──────────────────────────────────────────────────────────────┐
│          应用层 (Vue 3 + AntV G6 + ECharts)                    │
│  岗位发现 │ 能力更新 │ 图谱可视化 │ 匹配诊断 │ 趋势分析          │
└──────────────────────────┬───────────────────────────────────┘
                           │ RESTful API (JSON)
┌──────────────────────────▼───────────────────────────────────┐
│          分析层 (Pandas + NetworkX)                            │
│  时序图谱快照对比 │ 趋势预测 │ 人岗匹配评分 │ 图算法分析           │
└──────────────────────────┬───────────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────────┐
│          智能层 (讯飞星火API + LangChain + ChromaDB)             │
│  RAG检索增强 │ 实体抽取 │ 关系推理 │ 幻觉检测与事实校验           │
└──────────────────────────┬───────────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────────┐
│          知识层 (Neo4j + py2neo + BERT)                        │
│  NER实体抽取 │ 关系抽取 │ 实体对齐与消歧 │ 图谱版本管理           │
└──────────────────────────┬───────────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────────┐
│          数据层 (Scrapy + Playwright)                          │
│  多源爬虫集群 │ 数据清洗管道 │ MySQL + ES + 原始文件存储          │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 数据流

**采集流**：多源数据源 → Scrapy/Playwright 爬虫 → 数据清洗管道（去重/格式统一/质量评分）→ MySQL + ES

**知识流**：清洗后数据 → NLP 实体抽取（HanLP + 讯飞星火）→ 关系抽取 → 实体对齐与消歧 → Neo4j 图谱（带时间戳）→ 版本管理

**智能流**：用户查询 → RAG 检索增强（ChromaDB + LangChain）→ 讯飞星火 API 推理 → 结果结构化解析 → 幻觉检测（基于图谱回查）

**分析流**：Celery Beat 定时触发 → 时序图谱快照对比 → NetworkX 图算法 → 趋势预测 → MySQL (trend_analysis) → API → 前端图表

| 图表可视化 | Apache ECharts 5 | 大屏展示效果好，文档完善 |
| RAG 框架 | LangChain + ChromaDB | 检索增强生成，减少幻觉 |
| 后端框架 | FastAPI (Python 3.10+) | 异步高性能，原生 Swagger 文档 |
| 前端框架 | Vue 3 + TypeScript + Vite + Pinia | 生态成熟，构建快 |
| UI 组件库 | Element Plus | 企业级 Vue 3 组件库 |
| 数据分析 | Pandas + NetworkX | 数据清洗 + 图算法（中心性、社区发现） |
| 简历解析 | 讯飞文档解析 + 自定义 NER | OCR 处理 PDF/图片，结合微调 NER 提取字段 |
| 异步任务 | Celery + Redis | 异步处理爬虫、NLP、分析任务 |
| 部署 | Docker Compose | 一键部署全栈服务 |

### 大语言模型选型

| 模型 | 用途 | 说明 |
| --- | --- | --- |
| **讯飞星火 X2 / 4.0 Turbo** | 核心推理引擎 | 实体抽取、关系推理、人岗匹配、趋势预测 |
| **讯飞星火 X1.5** | 复杂推理任务 | 多跳推理、能力差距分析、学习路径规划 |
| **BGE-M3 / bge-large-zh** | 文本向量化 | 语义编码，岗位描述向量化 |
| **ChatGLM3-6B** | 本地备用模型 | 离线场景或隐私敏感任务 |

### NER "大模型+小模型"协同策略

用讯飞星火做 few-shot 标注生成训练数据，再微调 BERT-CRF / GlobalPointer 等轻量 NER 模型，兼顾标注质量与推理效率。

## 七、数据源方案

### 7.1 三类以上数据源

| 类别 | 具体来源 | 采集方式 |
| --- | --- | --- |
| **招聘平台** | Boss 直聘、智联招聘、拉勾、讯飞招聘官网 | Scrapy + Playwright 动态渲染 |
| **企业官网** | 目标企业招聘页面（如华为、百度、阿里、腾讯等 AI 企业） | Scrapy 定制爬虫 |
| **行业报告** | 中国信通院、IDC、Gartner 等发布的 IT 人才报告 | PDF 解析 + NER 提取 |
| **政策文件** | 各地政府数字经济/人工智能产业政策文件 | PDF 解析 |
| **学术论文** | CNKI、arXiv 等关于岗位技能演化的研究文献 | 数据集导入 |

### 7.2 数据质量标准

- 去重：基于 URL + 标题 + 公司 + 发布时间的复合 key
- 格式标准化：统一岗位名、技能标签、薪资单位、地点格式
- 异常值检测：薪资范围异常、发布时间异常、空字段率过高
- 每条数据标注时间戳和来源

## 十三、风险与应对

| 风险 | 等级 | 应对措施 |
| --- | --- | --- |
| 爬虫被反爬封锁 | 高 | IP 代理池 + UA 轮换 + 频率控制；准备公开数据集兜底；必要时手动采集补充 |
| 多源数据融合质量 | 高 | 建立标准岗位词典和技能标签词典；规则映射 + 相似度匹配兜底 |
| 实体抽取质量不达标 | 中 | 大模型+小模型协同策略：先用星火 few-shot 标注，再微调 BERT-CRF；规则模板补充覆盖 |
| 演示数据量不足 | 中 | 爬虫增量采集 + Kaggle 公开数据集；必要时用星火大模型生成模拟数据 |
| 星火大模型 API 调用不稳定 | 中 | 关键问答预置缓存回复；设计本地 BERT 兜底方案 |
| 三项准确率难以达到 90% | 中 | 提前设计准确率评测方案；构建高质量人工标注测试集；预留调优时间 |
| 实体消歧困难 | 中 | 建立实体别名映射词典；大模型辅助消歧 + 人工校验 |
| 团队协作冲突 | 低 | 接口预先定义好（见 `dev-spec.md`），Swagger 文档驱动开发 |

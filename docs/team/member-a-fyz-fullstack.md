# 成员 A：FYZ 管理与决策端全栈

## 1. 职责

负责 `fyz-src/frontend` 及其直接依赖的管理端后端能力，前后端由同一人闭环：

- 登录、岗位管理、岗位版本和技能抽取操作；
- 图谱、趋势、能力变化和系统管理页面；
- `analysis`、岗位版本、`admin` 真实 API 与对应 Service；
- 管理端 API 类型、状态管理、错误提示和操作审计。

不负责 JTT 求职流程、爬虫核心、Agent 推理框架和图谱底层同步算法。

## 2. 当前基线

- 已有认证、岗位 CRUD、版本、技能和图谱后端接口。
- 已有 Dashboard、JobManagement、GraphView、Trends、Admin 等页面。
- 能力动态更新需求已由 `analysis` 趋势接口和岗位版本接口覆盖；无消费者的旧 `/changes` 占位路由已移除。`admin` 已是真实管理接口。
- JD 生成 Agent 已提供任务创建、运行审计与可编辑草稿流程。
- FYZ 转岗指南已接入真实职业规划接口，支持文件文本提取、企业技术栈和内部岗位补充。
- FYZ 前端已有 Vitest 测试和 HTTP 数据 Provider。

## 3. 上下游接口

- 上游：成员 D 提供标准化数据，成员 E 提供图谱查询，成员 C 提供可解释分析。
- 下游：管理人员通过 FYZ 页面审核岗位、技能事实、图谱候选和系统任务。
- 与成员 F 共同维护 Pydantic Schema、OpenAPI、前端 TS 类型和 CI。
- 转岗页推荐卡只展示后端确定性分数，学习路径与解释来自成员 C 的结构化 Agent 输出。

公共接口改动必须先写 Schema 和示例，再同时更新前后端，不允许页面私自猜字段。

## 4. 4 周 MVP

### 第 1 周：基线与认证

- 跑通登录、Token 恢复、权限错误和退出流程。
- 统一管理端 API Client、加载态、空态和错误态。
- 核对岗位列表、详情、创建、编辑、删除和状态更新。

### 第 2 周：岗位与技能闭环

- 完成岗位版本查看和差异展示。
- 接入单岗位技能抽取与技能事实查看。
- 提供导入任务创建、进度轮询和失败原因展示。

### 第 3 周：图谱与趋势

- GraphView 使用真实 panorama、search、expand、tree 接口。
- 实现能力变化 MVP：按岗位比较两个版本的新增、删除和变化技能。
- 实现趋势 MVP：按技能频次、来源和时间展示基础趋势。

### 第 4 周：管理与演示

- Admin 展示任务、数据源、同步快照和系统健康信息。
- 完成全链路演示脚本：导入 → 审核 → 图谱 → 趋势。
- 补齐关键页面测试和失败场景。

## 5. 后 8 周优化

- W5-W6：批量操作、筛选、导出、版本审核和操作审计。
- W7-W8：趋势算法可视化、时间窗口、来源钻取和数据可信度展示。
- W9-W10：页面性能、图谱大数据量交互、响应式和无障碍。
- W11-W12：比赛演示模式、引导文案、截图、接口样例和回归测试。

## 6. 交付与验收

- 管理端所有可见操作连接真实 API，不保留伪成功按钮。
- 占位模块替换为真实 Service、Schema、测试和错误处理。
- 页面能说明数据来源、更新时间、任务状态和失败原因。
- 修改共享 API 时 JTT 兼容或提供明确迁移方案。


## 8. Git 建议

- 分支：`feat/a-job-version-diff`、`fix/a-admin-task-status`
- 提交：`feat(fyz-fullstack): add job version comparison`
- 每个 PR 只包含一个业务闭环，避免把所有页面积累到一个长期分支。

## 9. 主要风险

- 前端先造数据结构导致与 OpenAPI 漂移；
- 把占位接口误当成真实完成；
- 图谱页面加载过多节点；
- 管理端操作缺少确认、权限和审计信息。

# FYZ 端 MVP 开发规划

## 1. 目标与边界

本规划面向 FYZ 管理与决策支持端，优先形成可演示、可测试、可追溯的数据闭环：

> 真实岗位采集 → job-v1 校验 → MySQL 幂等入库 → 技能事实抽取 → 多来源验证 → 管理端展示结果

JTT 与 FYZ 后续可以分别设计接口字段和页面模型，但必须读取同一份 MySQL 业务数据。跨端共享采用稳定业务标识（岗位 ID、技能 ID、来源文档 ID），不要求两端 DTO 完全一致。

### 本轮纳入

- 科大讯飞招聘、智联招聘两个真实来源。
- 爬虫输出与后端导入字段统一。
- 数据文件安全选择、结构校验、幂等导入。
- FYZ 管理端触发采集，并展示校验和导入结果。
- 后端测试与前端构建验证。

### 本轮不纳入

- 新岗位发现和岗位能力动态演化算法。
- 多 Agent 编排、RAG、向量数据库。
- SimHash、Embedding 等复杂近似去重。
- 图谱人工审核全流程。
- JTT 页面和接口开发。

## 2. 当前状况

### 已具备

- FastAPI、Vue 3、MySQL、Neo4j 基础工程已经存在。
- 后端已有岗位导入、技能抽取、技能事实和跨来源验证能力。
- FYZ 管理端已有爬虫启动与轮询页面。
- 两个真实爬虫已经能够输出 JSON 文件。
- 数据库迁移、测试环境与统一 API 响应结构已经建立。

### 当前主要缺口

1. 爬虫输出使用 `post_date`、`duty`、`require`，导入服务读取 `posted_at`、`responsibilities`、`requirements`。
2. 导入服务只允许固定旧文件名，新生成的 `iflytek_N.json`、`zhaopin_N.json` 无法安全导入。
3. 导入前没有执行 job-v1 结构校验，错误数据可能进入抽取链路。
4. 管理端只显示“采集完成”，无法看到校验、重复和技能事实结果。
5. 管理总览仍含静态指标，不能作为比赛指标证明。

## 3. MVP 分阶段计划

### 阶段 0：固定可复现基线

目标：明确演示数据、运行方式和验收口径，避免后续结果不可复现。

- 固定两个数据来源：科大讯飞招聘、智联招聘。
- 使用最新 `iflytek_N.json`、`zhaopin_N.json` 作为采集产物。
- 定义 job-v1 必填字段、兼容字段和校验结果结构；源站未提供发布时间时保留空值并记录质量警告，禁止编造时间。
- 固定验证命令：后端定向测试、前端类型检查与构建。
- MySQL 作为两端共享事实源；Neo4j 仅作为可重建的图谱读模型。

验收：

- 至少能识别两个来源的最新输出文件。
- `python scripts/check_mvp_baseline.py` 能输出两个来源的记录数、失败数和质量警告数。
- 导入同一文件两次时，第二次不产生重复岗位。
- 校验失败的数据不会写入数据库。

### 阶段 1：采集、校验和入库闭环

目标：在 FYZ 管理端用一次操作走通真实链路。

后端任务：

1. 将爬虫输出统一为 canonical job-v1 字段：
   - `posted_at`
   - `responsibilities`
   - `requirements`
2. 导入端兼容旧字段：
   - `post_date → posted_at`
   - `duty → responsibilities`
   - `require → requirements`
3. 仅允许导入 `data` 目录内的受控 JSON 文件。
4. 在入库前完成逐条 schema 校验，失败则整批拒绝。
5. 返回以下结果：
   - 总记录数
   - 校验通过数、失败数
   - 成功入库数
   - 重复数
   - 技能事实数
   - 已验证/未验证事实数
6. 爬虫完成结果返回可导入文件名。

前端任务：

1. “立即执行”启动爬虫并轮询。
2. 爬虫成功后自动提交对应文件的导入任务。
3. 轮询导入任务并展示本次结果。
4. 失败时区分采集失败、校验失败和导入失败。

验收：

- 实际页面可以完成“采集 → 校验 → 入库”。
- 页面能看到本次处理结果，不再只显示一条成功提示。
- 原始 URL、抓取时间和来源得到保留；发布时间缺失时明确标记为未知。

### 阶段 2：技能事实审核 MVP

状态：已完成 MVP，不新增页面或路由，功能嵌入现有 `/admin` 系统管理页的“事实审核”分区。

- 展示技能、关联岗位、证据文本、来源链接、来源数、置信度、事实类型、抽取方式和验证状态。
- 支持按状态、关键词筛选和分页；支持管理员人工确认或填写原因后驳回未验证事实。
- 保存审核人、审核时间和审核意见；已经确认或驳回的事实不可重复决策。
- 人工驳回不会被后续跨来源自动验证覆盖。
- 审核接口只允许管理员访问；普通用户返回 403。
- 只有 `verified` 事实可进入正式图谱，`unverified` 和 `rejected` 均保留在 MySQL 作为可追溯事实。

### 阶段 3：岗位管理和图谱展示

状态：已完成 MVP，不新增页面或路由，功能嵌入现有 `/jobs` 和 `/graph` 页面。

- 岗位列表读取真实数据库。
- 岗位详情展示来源和技能证据。
- Neo4j 同步保持可重复执行，仅重建 `namespace=jiebang`。
- 默认、hybrid 和 http 三种前端数据模式的图谱均使用真实后端接口。
- Windows Celery worker 可连续执行异步任务，不复用已绑定到关闭事件循环的数据库连接。
- 现有“岗位洞察”页展示由标准岗位、岗位来源映射和已确认技能事实生成的技术栈基线与岗位参考标准。

### 阶段 4：趋势与演化分析

状态：已完成 MVP，功能嵌入现有 `/trends` 页面。

- 按发布时间窗口统计技能频次和岗位变化。
- 使用独立岗位簇和独立企业数，避免转载数据放大趋势。
- 输出变化证据，不由 LLM 直接生成增长结论。
- 对比期没有已确认事实时不输出增长结论，并在页面明确说明数据不足。
- 趋势页复用与岗位洞察一致的 `standard-job-v1` 基线，不维护第二份标准数据。
- 趋势时间范围固定为近 15 天、近 1 个月、近 3 个月、近 6 个月；短周期按日、长周期按月聚合。

### 阶段 5：Agent 增强

- Agent 只生成候选结果，不直接修改正式岗位或图谱。
- 保存输入证据、Prompt 版本、模型版本和运行记录。
- 对低置信度、新技能、新岗位进入人工审核。

### 阶段 6：JTT 共享数据接入

- JTT 使用独立 DTO 和接口，但复用 MySQL 中的岗位、技能和来源事实。
- 对同一岗位/技能增加跨端契约测试，验证展示语义一致。
- 禁止两端各自维护相互冲突的岗位事实副本。

### 阶段 7：比赛指标与交付

- 建立不少于 100 条带标注测试样本。
- 分别测量 JD 解析、简历解析、人岗匹配准确率。
- 后端单元测试覆盖率达到赛题要求。
- 完成真实浏览器演示回归、部署说明和答辩证据清单。

## 4. 阶段 0/1 实施顺序

1. 建立 job-v1 规范化与校验函数。
2. 修复两个爬虫的 canonical 输出字段。
3. 扩展安全文件规则，支持爬虫版本文件。
4. 将校验接入 ImportService，补充导入统计。
5. 在爬虫轮询结果中返回文件名。
6. 接入 FYZ 管理端自动导入和结果卡片。
7. 补充测试并执行后端测试、前端构建。

## 5. 测试与回滚

### 测试

- 合法 canonical 数据可导入。
- 旧字段数据可规范化后导入。
- 缺失必填字段或 JD 过短时整批拒绝。
- 路径穿越和非受控文件名被拒绝。
- 重复导入保持幂等。
- 采集、校验、导入三类错误在现有页面中给出不同提示。
- 技能事实审核列表、筛选、确认、驳回、重复决策和管理员权限均有接口测试。
- 人工驳回事实不会被自动跨来源验证改写。
- 采集岗位分页、筛选、详情来源和技能证据均有接口测试。
- 趋势统计按岗位簇、企业和地点去重，缺少对比基线时不输出新兴技能。
- Neo4j 全量同步连续执行两次后节点、关系和事实数保持一致。
- 前端接口类型、生产构建通过。

### 回滚

- 阶段 1 不修改数据库表结构；如自动导入出现问题，可仅停用自动提交，保留原爬虫运行功能。
- 阶段 2 新增 `job_skill_fact.reviewed_by`、`reviewed_at`、`review_note` 三个可空审计字段；使用 Alembic 版本 `20260729_0010`。
- 需要回滚阶段 2 时，先停用审核写接口，再执行 Alembic downgrade 到 `20260721_0009`；回滚会删除三项审核审计信息。
- 导入仍通过现有任务体系执行。

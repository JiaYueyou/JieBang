## 1. 本次修订结论

本次修订以以下业务事实为准：

1. 内部转岗由企业管理层发起和决策，不是员工自主选择岗位。
2. FYZ 是企业管理端，负责企业人才、内部岗位、技能需求、转岗规则和人岗决策。
3. JTT 是面向 C 端用户的求职端，不承接企业内部转岗流程，不读取企业人才池和内部私有岗位。
4. 岗位管理页面保留统一的岗位创建入口，但创建时必须先选择“公开招聘需求”或“内部私有需求”。
5. 公开招聘岗位和内部需求岗位可以在同一个管理页面中并列管理，但底层业务数据、接口、状态、权限和匹配关系必须隔离。
6. 岗位管理中的“已发布岗位”调整为双栏工作区：左侧为公开招聘信息，右侧为内部需求岗位信息，并分别筛选和操作。
7. 现有“转岗指南”页面全部重构为管理层使用的“内部转岗分析与决策中心”。
8. 管理层确定“人员 + 内部岗位”后，系统才能进入培养计划、联网资料搜索和 Word/PPT 生成阶段。

因此，上一版规划中以下方案不再适用：

- 不再由 JTT 用户选择企业内部目标岗位。
- 不再把内部转岗学习路径放入 JTT。
- 不再使用公开招聘 `JobPosting` 作为内部转岗目标岗位。
- 不再使用候选人 `Resume` 作为企业人才池员工档案。
- 不再让 Career Planning Agent 面向员工做自由职业选择。
- 不再在推荐阶段为多个岗位同时生成完整学习文件。

## 2. 产品问题与当前冲突

### 2.1 现有岗位模型只表达公开招聘

当前 `fyz-src/backend/app/models/job.py` 中的 `JobPosting` 包含公开发布、招聘人数、薪资、学历、招聘状态等招聘业务字段，页面操作也围绕“智能生成 JD”“发布岗位”“招聘中”设计。

内部需求岗位则属于组织编制和内部人才流动，业务字段包括接收部门、内部名额、来源部门限制、转岗窗口、职级范围、内部审批和计划到岗时间。两者不能只靠一个 `internal=true` 字段区分。

### 2.2 现有人才模型属于候选简历

当前 `Resume` 由上传用户所有，并直接与公开招聘岗位形成 `MatchRecord`。企业人才池需要管理企业员工编号、组织关系、当前岗位、职级、任职时间、能力证据和转岗状态，不能继续复用候选简历模型。

### 2.3 现有匹配关系错误连接内外部业务

当前匹配关系为：

```text
Resume → MatchRecord → JobPosting
```

内部转岗需要独立关系：

```text
EnterpriseTalentProfile → InternalMatchSnapshot → InternalPosition
```

公开候选人不能进入内部人才池，内部员工也不能因为存在能力画像而自动成为公开招聘候选人。

### 2.4 现有 Career Planning 候选岗位来源不符合新需求

当前 `CareerService` 从 `JobPosting.status == "open"` 的公开岗位中构建候选岗位。重构后，内部转岗分析只能读取已审批并处于内部开放状态的 `InternalPosition`。

### 2.5 原“转岗指南”是输入型演示页，不是管理决策页

现有页面依赖临时输入员工技能、企业技术栈和内部需求岗位，缺少企业人才池、内部岗位事实、规则版本、候选名单和管理决策记录。

新的转岗页面不应要求管理层反复复制粘贴信息，而应直接消费四个正式业务模块的数据。

## 3. 产品边界

### 3.1 FYZ 管理端

FYZ 负责：

- 维护公开招聘岗位。
- 维护内部私有需求岗位。
- 维护企业人才池。
- 维护企业数据技能需求库。
- 配置转岗规则。
- 运行“人找岗”和“岗找人”分析。
- 形成候选名单。
- 由管理层确定人员和岗位。
- 记录转岗决策、审批和状态。
- 在决策后生成培养计划和学习材料。
- 查看 Agent 运行、规则版本、数据质量和审计记录。

### 3.2 JTT C 端

JTT 继续负责：

- 公开岗位探索。
- C 端用户简历管理。
- 公开岗位匹配。
- 求职辅助和个人公开市场学习内容。

JTT 明确不负责：

- 查看内部私有岗位。
- 访问企业人才池。
- 发起企业内部转岗。
- 确认企业内部目标岗位。
- 查看企业转岗规则。
- 下载企业内部转岗材料。

如果未来需要员工在线查看企业安排的培养计划，应新建企业员工门户或 FYZ 下的员工个人角色，不能直接复用 JTT 的 C 端身份体系。

建议将 FYZ 菜单分为三个业务分组。

### 4.1 岗位与人才

- 岗位管理

### 4.2 内部转岗

- 转岗分析与决策
- 转岗规则
- 转岗记录
- 培养计划与材料

### 4.3 外部招聘与系统治理

“岗位管理”可以在一个页面中管理两类岗位，但页面必须明确分区；“外部人才匹配”和“内部转岗分析”必须是两个独立页面。

## 5. 岗位管理页面重构

当前页面：`fyz-src/frontend/src/views/JobManagement.vue`

### 5.1 发布岗位增加需求类型

岗位创建表单第一项增加必选字段：

```text
需求类型
○ 公开招聘需求
○ 内部私有需求
```

该字段必须在调用 Agent、生成描述或保存草稿前确定。保存后不允许直接把内部岗位转换为公开招聘岗位，反之亦然；如需改变业务类型，应复制为新岗位并重新审核。

原因是两类岗位的权限、状态和后续匹配链路不同，直接切换会导致历史记录、候选人或员工关联错误。

### 5.2 公开招聘需求表单

保留现有主要字段：

- 岗位名称。
- 所属部门。
- 岗位级别。
- 招聘人数。
- 工作地点。
- 薪资范围。
- 学历与经验要求。
- 岗位职责。
- 任职要求。
- 必备技能和加分技能。
- 对外 JD。
- 草稿、招聘中、已关闭状态。

公开招聘岗位继续进入：

- JTT 岗位列表。
- C 端简历匹配。
- 外部人才匹配。
- 外部招聘统计与趋势分析。

### 5.3 内部私有需求表单

内部岗位使用独立字段：

- 内部岗位名称。
- 接收部门。
- 接收负责人。
- 岗位职级或职级范围。
- 内部开放名额。
- 开放原因：组织调整、项目需要、人员补充、战略储备等。
- 内部岗位职责。
- 必备技能。
- 可培养技能。
- 最低司龄。
- 当前岗位最低任职时间。
- 允许来源部门。
- 禁止或限制条件。
- 计划到岗时间。
- 内部开放起止时间。
- 审批人或审批流程。
- 内部说明，不生成对外 JD。

内部岗位状态建议使用：

```text
draft            草稿
pending_approval 待审批
open             内部开放
paused           已暂停
filled           名额已满
closed           已关闭
```

内部岗位只能进入：

- FYZ 内部岗位列表。
- 企业技能需求库。
- 转岗分析与决策。
- 内部培养计划。

内部岗位不得进入 JTT、公开岗位接口、外部候选人匹配和公开招聘统计。

### 5.4 Agent 辅助内容差异

岗位描述 Agent 需要根据 `demand_type` 使用不同 Prompt 和 Schema。

公开招聘模式输出：

- 对外职责。
- 任职要求。
- JD 文本。
- 招聘技能建议。

内部需求模式输出：

- 内部岗位职责草案。
- 企业技能要求草案。
- 可培养技能建议。
- 转岗适用人员特征。
- 需要管理层确认的组织约束。

内部模式不输出薪资宣传、企业招聘宣传或对外 JD 文案。

### 5.5 “已发布岗位”双栏工作区

桌面端采用左右双栏：

```text
┌──────────────────────────────┬──────────────────────────────┐
│ 公开招聘信息                  │ 内部需求岗位                  │
│ 数量、筛选、公开状态          │ 数量、筛选、内部开放状态      │
│ 公开岗位表格                  │ 内部岗位表格                  │
└──────────────────────────────┴──────────────────────────────┘
```

左侧“公开招聘信息”建议展示：

- 岗位名称。
- 部门。
- 招聘人数。
- 工作地点。
- 招聘状态。
- 发布日期。
- 外部候选人数。
- 编辑、关闭、复制、查看匹配人才。

左侧筛选：

- 关键词。
- 部门。
- 招聘状态。
- 工作地点。
- 发布时间。

右侧“内部需求岗位”建议展示：

- 内部岗位名称。
- 接收部门。
- 职级范围。
- 内部名额。
- 内部状态。
- 有效期。
- 符合资格人数。
- 高匹配人数。
- 编辑、提交审批、暂停、关闭、查看适配员工。

右侧筛选：

- 关键词。
- 接收部门。
- 内部状态。
- 职级。
- 开放时间。
- 是否存在候选人。

双栏应分别维护分页、排序和筛选状态，不能使用一个筛选条件同时改变两栏结果。顶部可以提供全局搜索，但结果必须按岗位类型分组展示。

在窄屏下可以降级为“公开招聘 / 内部需求”两个页签，不能强行保留过窄双栏。

### 5.6 视觉和交互约束

- 公开岗位统一使用“公开招聘”蓝色标识。
- 内部岗位统一使用“内部私有”橙色或紫色标识。
- 内部岗位名称、详情、接口响应均不得被 JTT 路由获取。
- 删除、关闭、暂停和审批使用不同操作文案，避免把内部“暂停”误解成公开“停止招聘”。
- 创建按钮可以保持一个，但弹窗或表单必须先选择需求类型。

## 7. 企业数据技能需求库

### 7.1 产品目标

回答企业内部“需要什么技能、需要多少、当前供给多少、缺口多大”。它不是简单的技能名称列表。

### 7.2 数据内容

- 企业技能名称和标准名称。
- 技能类别与层级。
- 需求部门。
- 关联内部岗位。
- 必备或可培养。
- 需求人数。
- 当前具备人数。
- 供需缺口。
- 战略优先级。
- 生效时间。
- 内部来源和证据。
- 人工确认状态。

### 7.3 数据来源

首版只使用内部来源：

- 内部开放岗位。
- 企业技术战略。
- 部门人工维护。
- 内部项目需求。
- 已批准的人才发展计划。

公开招聘和外部市场趋势可以保留为独立洞察，但不能自动写入内部技能需求，也不能直接影响内部转岗评分。

### 7.4 页面功能

- 按部门、内部岗位、类别和优先级筛选。
- 查看技能需求、内部供给和缺口。
- 查看关联内部岗位。
- 查看具备该技能的企业员工。
- 新建和调整企业技能需求。
- 审核 Agent 发现的候选技能。
- 查看需求版本变化。

## 8. 转岗规则

### 8.1 硬性规则

不满足时不能进入候选名单，例如：

- 最低司龄。
- 当前岗位最低任职时间。
- 职级范围。
- 部门或地点限制。
- 必备资格和认证。
- 是否允许跨序列转岗。
- 企业规定的其他资格条件。

### 8.2 软性评分规则

通过硬性资格后用于排序，例如：

- 技能匹配度。
- 可迁移能力。
- 项目经验。
- 相近岗位经历。
- 培养周期。
- 内部岗位紧缺程度。
- 技能差距数量。
- 转岗风险。

### 8.3 页面功能

- 创建规则集。
- 设置适用岗位、部门或职级范围。
- 配置硬性条件。
- 配置评分权重。
- 设置推荐阈值和风险等级。
- 使用历史数据模拟。
- 发布、停用和复制规则版本。
- 查看某次匹配使用的规则快照。

每次匹配必须保存规则版本，后续调整规则不能覆盖历史决策依据。

## 9. “转岗指南”页面整体重构

当前页面：`fyz-src/frontend/src/views/CareerGuide.vue`

建议保留现有路由兼容，但页面标题由“转岗指南”调整为“转岗分析与决策”；也可以在后续路由重构时使用 `/internal-transfer`。

### 9.1 删除现有页面功能

删除或迁移以下临时输入：

- 员工当前技能自由文本。
- 临时上传员工简历。
- 企业技术栈自由文本。
- 内部需求岗位逗号输入。
- 企业内部文件临时上传。
- 面向员工的“详细学习计划”按钮。
- 收藏内部岗位。

这些数据应该分别来自企业人才池、内部岗位、技能需求库和转岗规则。

### 9.2 新页面顶部决策概览

展示：

- 企业人才总数。
- 当前内部开放岗位数。
- 待评估员工数。
- 已形成候选关系数。
- 待管理层决策数。
- 进行中的转岗案例数。
- 数据最后更新时间。
- 当前生效规则版本。

### 9.3 两种分析入口

#### 人找岗

管理者先选择员工，系统分析其适合哪些内部岗位。

输入：

- 员工或员工集合。
- 可选目标部门。
- 可选内部岗位范围。
- 生效规则版本。

输出：

- 是否满足转岗基础资格。
- 推荐内部岗位。
- 匹配度。
- 已具备技能。
- 缺失技能。
- 预计培养周期。
- 风险等级。
- 推荐原因和证据。

#### 岗找人

管理者先选择内部岗位，系统筛选适合的企业员工。

输入：

- 内部岗位。
- 可选来源部门。
- 候选职级范围。
- 匹配度阈值。
- 生效规则版本。

输出：

- 满足硬性资格人数。
- 候选员工排名。
- 当前部门和岗位。
- 综合匹配度。
- 技能差距。
- 预计培养周期。
- 转岗风险。

### 9.4 人岗匹配矩阵

核心表格字段：

- 员工姓名。
- 当前部门和岗位。
- 目标内部岗位。
- 接收部门。
- 硬性资格结果。
- 综合匹配度。
- 已具备技能。
- 关键缺失技能。
- 预计培养周期。
- 风险等级。
- 规则版本。
- 数据更新时间。

操作：

- 查看匹配证据。
- 生成 Agent 解释。
- 加入候选名单。
- 与其他员工或岗位比较。
- 标记暂不考虑。
- 提交管理层决策。

### 9.5 候选比较

支持两类比较：

- 同一员工比较多个内部岗位。
- 同一内部岗位比较多个员工。

比较维度包括：

- 硬性规则是否通过。
- 技能匹配度。
- 可迁移能力。
- 关键技能缺口。
- 预计培养周期。
- 原部门影响。
- 接收部门适配性。
- 风险和待确认事项。

### 9.6 管理决策

管理层在系统中确定：

- 转岗员工。
- 目标内部岗位。
- 接收部门。
- 计划到岗日期。
- 决策说明。
- 是否进入培养期。
- 后续审批或沟通负责人。

决策操作必须生成不可被 Agent 覆盖的 `TransferDecision` 记录，并保存：

- 人才画像快照。
- 内部岗位快照。
- 技能需求快照。
- 匹配结果。
- 规则版本。
- Agent 解释版本。
- 决策人和决策时间。

### 9.7 转岗案例状态

建议状态：

```text
draft              分析草稿
shortlisted        已进入候选名单
pending_decision   待管理层决策
confirmed          已确定人岗
development        培养准备中
pending_transfer   待办理转岗
transferred        已完成转岗
cancelled          已取消
```

## 11. 管理层确定人岗后的培养材料

联网搜索、Word 和 PPT 保留为后续能力，但触发位置改到 FYZ。

触发前提：

- 已存在正式 `TransferDecision`。
- 已确定一名员工和一个内部岗位。
- 内部岗位和技能需求仍处于有效版本。
- 操作人具备培养计划生成权限。

生成流程：

```text
管理层确认人员和岗位
→ 搜索内部允许的官方资料和权威内容
→ 校验来源、时效和 URL
→ 生成结构化培养计划
→ 生成 Word / PPT
→ FYZ 下载或分配给员工
```

首版不把内部培养材料放到 JTT。如果未来需要员工在线学习，应单独建设企业员工入口。

## 14. 权限规划

建议至少区分：

### 系统管理员

- 配置系统和 Agent。
- 管理接口密钥和运行参数。
- 不因技术权限自动获得全部人才业务决策权。

### HR / 人才发展负责人

- 管理企业人才池。
- 管理技能需求和转岗规则。
- 查看候选关系和转岗案例。
- 发起培养计划。

### 部门负责人

- 创建本部门内部需求岗位。
- 查看权限范围内的候选员工。
- 提交候选意见。

### 管理决策人

- 比较人岗方案。
- 确定人员和岗位。
- 提交决策说明。

### 只读审计角色

- 查看已授权范围内的规则版本、决策快照和运行记录。
- 不能修改人才、岗位或决策。

所有企业人才、内部岗位和转岗案例接口必须进行权限检查，不能只依赖前端隐藏菜单。

- 企业技能需求不从公开岗位自动生成。
- 可从技能需求查看关联内部岗位和具备技能的员工。

### 阶段 3：转岗规则与确定性匹配

开发内容：

- 新建规则集、规则版本和模拟能力。
- 实现硬性资格过滤。
- 实现软性评分。
- 实现人找岗和岗找人。
- 保存匹配快照、规则版本和证据。

验收标准：

- 不满足硬性规则的员工不能进入正式候选名单。
- 每个分数都可以解释到规则和证据。
- 修改规则后不覆盖历史匹配快照。
- 没有 LLM 时也能完成基本匹配。

### 阶段 4：“转岗指南”页面重构

开发内容：

- 删除临时文本和文件输入式页面。
- 新增决策概览。
- 新增人找岗和岗找人入口。
- 新增匹配矩阵和候选比较。

- 新增管理决策和转岗案例状态。

验收标准：

- 页面只读取企业人才、内部岗位、内部技能需求和转岗规则。
- 可以完成“分析 → 候选 → 比较 → 确定人岗”。
- 决策保存完整快照和操作人。
- Agent 失败不影响确定性结果展示。

### 阶段 5：Career Planning Agent 管理增强

开发内容：

- 重写 Agent Schema 和 Prompt。
- 输入内部人岗匹配快照和证据。
- 输出匹配解释、风险、待确认事项和培养建议。
- 复用现有异步任务和降级机制。

验收标准：

- Agent 不读取公开岗位。
- Agent 不修改分数和资格结果。
- Agent 输出通过 Schema 和业务资源存在性校验。

### 阶段 6：培养计划、搜索与 Word/PPT

开发内容：

- 仅允许已确定人岗的转岗案例触发。

- 校验官方来源、时效、URL 和内容指纹。
- 生成结构化培养计划。

- 私有存储、鉴权下载、版本和分配记录。

验收标准：

- 未确定人员和岗位时不能生成材料。
- 文件中的员工、岗位、技能差距和资料来源可追溯。
- 内部材料不进入 JTT。
- 失败时可以独立重试搜索、内容生成或文件渲染。

### 阶段 7：审计、效果和运营优化

- 内部技能缺口变化。

- 内部资料失效检查。

## 17. 端到端验收流程

完整流程应验证：

1. 管理员在岗位管理中选择“公开招聘需求”，创建公开岗位。
2. 公开岗位出现在左侧列表，并可被 JTT 查询。
3. 管理员选择“内部私有需求”，创建内部岗位。
4. 内部岗位出现在右侧列表，但 JTT 和公开岗位接口无法查询。
5. HR 导入企业员工并形成能力画像。
6. 内部岗位技能进入企业技能需求库。
7. 管理员发布一套转岗规则。
8. 管理层通过“人找岗”查看某员工适合的内部岗位。
9. 管理层通过“岗找人”查看某岗位适合的企业员工。
10. 系统生成确定性匹配结果和证据。
11. Agent 对确定性结果生成解释，但不修改分数。
12. 管理层将人岗关系加入候选名单并完成比较。
13. 管理层确定一名员工和一个内部岗位。
14. 系统保存决策、岗位、人才、规则和匹配快照。
15. 已确定案例可以生成培养计划和 Word/PPT。
16. 未授权用户不能查看内部岗位、企业人才和内部材料。

## 19. 推荐的第一期开发目标

第一期不以 Word/PPT 为目标，而以内部转岗业务闭环为目标：

```text
岗位管理区分公开与内部需求
→ 企业人才池

→ 转岗规则
```

在这一基础闭环稳定后，再进入 Agent 深度解释、联网搜索、培养计划和 Word/PPT 生成。
